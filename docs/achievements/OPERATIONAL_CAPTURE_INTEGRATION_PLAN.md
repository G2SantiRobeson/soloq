## 4. Contrato entre syncWrite y repositorio D

### Respuestas A–F de la inspección

**A. Reutilizable, no directamente invocable en SW:** conceptos de insertHeader/insertUnits (unicidad, comparación, transiciones, límites, JSON, rollback); revision/recover/list para revisión/recuperación/lectura por dueño; effective para proyección a R; cascadas/deleteEvidence para D13 local. prepareSeal/seal/reproduceSeal/sealState son solo estructura sintética y comparación local: no son productores de reconciliación operacional y se dejan fuera de E.2.

**B. Dependencia PGlite:** `LocalDatabase = PgliteDatabase<typeof schema>` y `LocalTransaction = Pick<LocalDatabase, select|insert|update|delete>`. Todos los métodos usan esa inyección; los de escritura y varias lecturas llaman database.transaction. No se encontró SQL privativo de PGlite en sus algoritmos, pero tipos/builders/adaptadores, serialización bigint y comportamiento de aislamiento deben probarse, no resolverse con un cast.

**C. Inyección:** posible como diseño, **no soportada hoy por una API InTx existente**. Extraer una primitiva con el mínimo puerto de Drizzle compatible con `SyncTransaction` postgres-js y el transaction PGlite de tests; recibe tx y contexto de revisión, nunca db()/DATABASE_URL/constructor de conexión. Comprobar ambos tipos con TypeScript estricto. La API instalada postgres-js abre begin para transaction del database y savepoint para transaction anidada del tx. Usar el database externo dentro de SW puede abrir otra transacción/conexión y perder atomicidad; forzar el tx al tipo PGlite no arregla duplicación de revisión/aislamiento. Se propone **cero transaction/savepoint interno** en primitivas SW.

La entrada operacional debe exigir el cliente ligado al owner vigente de `withSyncLease`, además de rechazar Demo antes de IO. El camino de dominio unleased que syncWrite conserva para tests no se convierte en un productor real. runId puede faltar en operaciones existentes sin progreso: no es autorización ni identidad de scan; el owner/fencing del lease continúa siendo obligatorio.

**D. Locks:** SW toma primero fila del lease. En partida compartida, match lock → descubrir asociados → todos los players por UUID; después headers del dueño y unidades por orden estable. Ranked/página/identidad sin match: lease → players → headers. No invocar owner(lock) de D antes de lock de match en una unidad que después reclasifica/asocia: invierte el orden. Reutilizar la fila ya protegida dentro del mismo tx es seguro, pero redundante; el puerto valida dueño/scope sin tomar otro lease ni abrir lectura repeatable read dentro de SW. DELETE conserva su camino; carreras se prueban en F.

**E. Revisiones:** hoy insertHeader incrementa, insertUnits incrementa por lote y E.1 flush incrementa; llamarlos juntos sumaría varias R. Primitiva operacional sin incremento propio, marca `markSourceChanged(tx, playerId)` cuando confirma algo nuevo. Cada unit de la SW usa R_destino obtenido **por SQL `source_revision + 1` bajo lock** para ese dueño, no JS R+1; E.1 flush realiza la única suma antes del fencing final. Header/páginas/disposiciones/contexto/fuente de ese commit comparten R_destino. Sin nuevos datos ni contexto no marcar y no sumar. Nueva recepción real con otro captureId no es retry idéntico aunque su contenido coincida. Overflow revierte toda la unidad.

**F. Separación:** D v1 declared synthetic/unknown, sellos nature synthetic y B/C `provenanceAuthentication: not_performed` quedan tal cual. Nuevo contrato privado operacional con versión y procedencia de recepción del servidor; proyección explícita a declaraciones B/C, cuando se autorice, conserva sus bloqueos y nunca cambia grantAuthorized/certification. No llamar `simulateBadgeVerification` desde sync/render.

### Flujo transaccional propuesto (no código)

1. Antes de SW: el cliente recibe/valida; factoría privada materializa payload mínimo, versiones, ID/fecha reales, tamaño y huella acotada. No Riot/hash de temporada bajo locks.
2. SW hace fencing actual, luego locks correctos según la fuente. Releer pertenencia/eligibilidad/identidad y fuente compartida donde sea necesario.
3. Recuperar cabeceras/clave idempotente y contenido almacenado en consultas agrupadas; obtener R_destino por SQL para cada dueño protegido. Resolver referencia de captura/scan y predecessor en esa fotografía.
4. Insertar fuente, cabecera/unidades y cambiar cursor/metadata activo en el mismo tx. Si una dimensión falla, no publicar ni avanzar la unidad. Insertar unidades en lotes ≤100 dentro de la misma SW, sin que cada lote sume otra R.
5. Marcar dueño(s) solo si hubo cambio nuevo; E.1 flush agrupa una suma por dueño. SW conserva sus checkpoints agrupados y fencing final; solo tras commit se publica el avance en memoria.

**PROPUESTA — idempotencia de scan:** scanId de servidor distinto de runId/requestId y durable en cabecera. Header operationKey incluye fase/cola y ese identificador opaco; units incluyen captura/offset/intento o disposición/predecessor. Ordinal único y progreso interno bajo lock de header, límites congelados, sin derivar hechos de contador. Un retry de **persistencia** recupera por clave+contenido antes de repetir y puede reutilizar captura recibida en memoria; después de reinicio recuperar lo confirmado. Si hubo una nueva petición Riot, registrar nueva recepción/attempt, no copiar receivedAt anterior ni sobrescribir lista contradictoria.

Metadata activa por dueño/fase/cola en JSON requiere contrato de actualización propio: el insertHeader D actual coteja toda data inmutable; no puede tratarse su API como upsert mutable. Definir parte immutable/parte lifecycle y huellas correspondientes, compare protegido y lectura V1/V2 explícita. No afirmar que el schema por sí solo impide múltiples activos. Rechazar ambigüedad; no escoger por createdAt el que favorezca un resultado.

## 5. Factoría privada de procedencia

**HECHO VERIFICADO.** RiotClient.request retorna solo parsed.data. No conserva receivedAt, captureId, estado/attempt de cada respuesta ni vínculo durable al cliente/endpoint. Account/league/match schemas prueban forma; no autentican un objeto suministrado. request(host,path,schema) y Dependencies permiten inyección para tests; server-only no basta para distinguir fixtures de proveedor real.

**PROPUESTA.** Factoría interna con tokens opacos ligados en WeakMap privado a la instancia de cliente creada por la entrada autorizada del servidor. El punto de recepción del cliente produce el token tras respuesta real, lectura del cuerpo y validación; identidad/routing/endpoint permitidos se vinculan a la operación interna, no a URL/header/cookie del usuario. Fixtures usan una factoría separada `synthetic`; no obtienen origen real por declarar host, source o receivedAt. No exponer endpoint que acepte capturas ni un constructor público de evidencia autenticada.

Contrato mínimo propuesto: formato/normalizer/classifier versions; captureId UUID de servidor; owner playerId/plataforma/cola/temporada; categoría endpoint sin path identificable; outcome/status/attempt; receivedAt real del punto de recepción de cuerpo validable (para HTTP error, recepción del status); validatedAt cuando la validación termina; parámetros efectivos permitidos; payload mínimo; huella de contenido y metadatos, sin autorreferencia; asociación a R/scan/source ID **al confirmar SW**. En fallo de red no hay receivedAt: failedAt local nullable outcome network, no respuesta inventada. Tiempo de BD createdAt/commit no se llama receivedAt. Un UUID/hash no constituye firma de Riot.

Una respuesta all-queues o una reclasificación compartida puede producir varias proyecciones personales: **un receptionId opaco identifica la recepción real**, y cada captureId identifica su proyección de owner/cola/versiones. Todas conservan la misma fecha y categoría de esa recepción, sin presentar dos requests porque haya dos cabeceras. Cada captureId tiene contenido/metadatos inmutables propios; no reutilizar el mismo captureId para proyecciones diferentes, que los prototipos detectarían como contradicción. receptionId no es autorización, FK global ni lugar para retener payload personal sin dueño; las copias mínimas desaparecen con cada owner.

Comprobar vínculo de cuenta usando PUUID exclusivamente en memoria y la columna existente protegida, sin guardar otra copia, hash personal o URL. Valores de participante comprobados contra ese vínculo; presencia duplicada se señala como ambigüedad probatoria. Si se desea cambiar el comportamiento observacional ante esa ambigüedad, requerirá corrección de ingesta expresamente aprobada; captura no la resuelve escondiéndola.

| Nivel | Significado y transición permitida |
| --- | --- |
| Recibida | Respuesta efectivamente obtenida en esa petición; aún puede ser inválida o perderse antes de commit. |
| Validada | Cumple schema y controles de vínculo/ámbito específicos; no demuestra cobertura. |
| Confirmada en BD | Captura mínima/fuente asociada/cursor/R confirmaron juntos. Solo aquí hay evidencia durable de la recepción bajo la confianza del servidor. |
| Fuente existente sin captura | Dato almacenado; concordancia de valor no crea recepción histórica. Puede enlazarse a una nueva recepción real solo como comprobación **actual**, sin fecha retroactiva ni elevación automática. |
| Legacy | Origen/recepción anteriores desconocidos, fechas de captura null. No rellenar desde updatedAt/rankCheckedAt/defaultNow. |
| Manifiesto estructural | Cadena/concordancia de declaraciones suministradas, con unknowns y contradicciones preservados. No origen operacional por sí solo. |

## 6. Política de 404, unknown, legacy y ventanas

**PROPUESTA.** Conservar 404 como intento temporal con ID y fecha real; no declarar desaparición permanente. Mantener ingesta actual sin fabricar detalle. Un scan de importación puede terminar con 404 y recent coverage avanzar, pero su evidencia queda blocked/incomplete. Retry futuro solo cuando los caminos vigentes ya consulten o haya autorización nueva; no petición adicional para completar una insignia.

IDs originales repetidos no se eliminan de páginas capturadas; el trabajo sigue deduplicado como hoy. Las disposiciones por scope ranked incluyen otra cola/modo/intervalo con fundamento; si falta detalle que permita excluir, unknown. No interpretar cada pending como derrota ni producir un porcentaje de toda la temporada. Offset de Riot, orden de IDs y orden competitivo por timestamp son cosas distintas.

Scan histórico legacy retomado en offset>0 o pending heredados: registrar prefijo desconocido y las páginas que realmente se reciben desde ahora; ninguna página reconstruida desde discovered/processed. C exige cadena desde cero: ese prefijo impide recibo completo de ese scan, aunque continúe y completed sea correcto observacionalmente. Próximos incrementales son scopes nuevos y no reparan retrospectivamente el prefijo.

Recent conserva su reinicio desde offset 0 y overlap 24 h; persistir scan de **evidencia** no cambia su algoritmo ni añade un cursor de ingestión. Distintos start/end efectivos → nuevo scan; parámetros iguales y raíz activa inequívoca → intentos asociados, sin declarar índice congelado. Conservar terminal aun si se alcanza límite antes de detalles. Las páginas que nunca se pidieron no aparecen como recibidas.

Histórico valida detalle frente a temporada y consulta con segundos redondeados; recent valida su ventana semiabierta. Guardar objetivo preciso, límites reales del request y filtro local por separado; si no concuerdan, conservar incertidumbre/contradicción, no alterar parámetros, timestamps o datos para pasar C. Semántica Riot de límites/índice y margen/plazo recuperable sigue DECISIÓN PENDIENTE. Ningún cierre OTP con endAt desconocido.

## 7. Atomicidad, crashes y reintentos

| Escenario | PROPUESTA de respuesta segura | Prueba futura |
| --- | --- | --- |
| Crash antes de commit | No fuente/captura/cursor/R de esa unidad; mantener último checkpoint confirmado. Respuesta en memoria perdida no se registra como recibida retrospectivamente. | Fault injection tras cada insert/update, rollback de todo el prefijo. |
| Crash después de commit / respuesta perdida | Recuperar por owner/scan/clave; fuente/captura/cursor/R ya existen. No interpretar timeout como rollback. | Reiniciar repositorio/contexto, retry idéntico devuelve mismo estado sin R extra. |
| Retry DB idéntico | Misma captureId+contenido, claves/ordinal/predecessor concordantes: no otra recepción ni suma. | Misma página/disposición dos veces, SQL/real float4 exacto de E.1 intacto. |
| Nueva respuesta para offset conocido | Nueva captureId/attempt con fecha real; conservar respuestas anteriores. Listas distintas son contradicción de índice, no reemplazo favorable. | Éxito→éxito distinto, fallo→éxito, éxito→fallo y captura ID reutilizada con contenido distinto. |
| Fuente vieja y respuesta nueva discordantes | SourceConflict mantiene rollback de unidad. No confirmar una captura como asociación exitosa. Si se conserva diagnóstico de conflicto, segunda SW **evidencia-only**, fenced, sin consumir cursor ni sobrescribir fuente, con formato de corrección separado del terminal D. | Fuente previa intacta, conflicto durable no resolved; si segunda SW falla, ninguna afirmación probatoria de ese intento. |
| 404/exclusión | Captura/disposición y cursor de consumo juntos; sin fila de detalle inventada. | Disposición persiste aunque imported=0; terminal no borra gap. |
| Página terminal | Página original en SW de descubrimiento; fin de importación después de consumo y en SW final. No seal operacional. | Página vacía/corta seguida de crash/reload; completed con gaps sigue no probatorio. |
| Lease expirado/fencing rechazado | Toda nueva evidencia participa del mismo rollback de syncWrite, incluido R. El writer no usa una conexión sin lease para salvar progreso a destiempo. | Fencing final tras inserción y flush; takeover real pendiente F. |
| DB perdida | No afirmar captura confirmada. Puede ser respuesta de commit perdida: consultar claves al recuperar, no repetir ciegamente. | Fallo previo a commit vs pérdida de respuesta posterior; memoria/DTO no suplantan BD. |
| Captura inválida/tamaño/cupo | Política A inicial: abortar unidad, cursor anterior disponible, error sanitizado. No truncar payload ni convertir fuente en atestada. | Exceso por fila/batch/owner y bytes reales, sin avance falsamente completo. |

Las recepciones de intentos internos de RiotClient requieren un hook privado acotado: no esperar SQL arbitrario en el pacing de cada retry. Conservar lo necesario en memoria hasta la unidad de persistencia; si una ejecución termina antes, solo quedan confirmados los intentos efectivamente guardados. Para fallos finales se permite SW de evidencia-only bajo lease vigente, sin presupuesto Riot nuevo; el callback de cooldown mantiene su prioridad. Una futura exigencia de historial durable **de cada despacho** implicaría escrituras y diseño adicionales; no se garantiza aquí sin medirlo. Un intento perdido no puede convertirse más tarde en prueba de ausencia de fallo.

## 8. Fallo de captura: alternativas y recomendación

| Alternativa | Garantía posible | Riesgo / coste / recuperación |
| --- | --- | --- |
| **A. Rollback de unidad que afirmaría conservar prueba** | Fuente/cursor/captura/R juntos o ninguno; reutiliza garantías E.1. No hay pérdida probatoria silenciosa. | Error de captura/cupo puede detener progreso observacional de ese jugador e inducir consultas repetidas en próximas ejecuciones. ## 9. Remakes compartidos y correcciones

**HECHO VERIFICADO.** isRemake usa some(true); todos los marcadores ausentes producen false. matches guarda solo bool nullable, así que no permite recuperar la base original. classifyStoredRemake E.1 bloquea match, descubre asociaciones bajo ese lock, bloquea players por UUID y marca todas sus revisiones si cambia bool. InsertMatchParticipation coordina nuevas asociaciones con la misma fila. El script actual no valida ID de respuesta contra solicitado.

**PROPUESTA.** Capturar `presentTrue`, `presentFalse`, `missing`, versión de clasificación y bool observacional actual, sin array de PUUID. Distinguir «false calculado por ausencia» de «marcadores explícitos false»; la suficiencia de marcadores mixtos para prueba queda pendiente. No cambiar current isRemake, matchOutcome, estadísticas ni exclusión observacional del motor. Proyección probatoria puede conservar unknown aunque el bool observacional sea false, mediante contrato explícito separado.

Reclasificación: comprobar identidad del match para poder atribuir captura real; preservar old/new y referencia a base anterior si existe. Bool igual pero **nueva base de evidencia** confirmada requiere R de todos los dueños que reciben esa evidencia, aunque E.1 sin capturas no sumaba por igualdad; retry idéntico de la misma captura no suma. No invocar classifyStoredRemake y después descubrir dueños por SELECT fuera de protección: mantener match lock y conjunto dentro de SW, copiar solo unidades mínimas owner-bound por cada afectado. Si no hay asociados, no crear huella personal global ni R de jugador inexistente.

Captura de otro dueño no atesta automáticamente la participación propia. Otra participación del mismo match necesita su vínculo/detalle normalizado; referencias del CHECK no cruzan owner/cola. Si el dueño fue eliminado, no se reconstruye desde nombre/PUUID ni se transfiere evidencia a un UUID recreado. Se conservan fuentes compartidas de otros jugadores y sus propias capturas. No sobreescribir terminal resolved de D; nueva cadena/captura de corrección según autorización, contradicción preservada y ningún regrant.
